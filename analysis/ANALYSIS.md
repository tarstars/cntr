## 2. The agent: a Cline fork with a stage machine and an external memory

**Lineage [code].** Fork of **Cline 3.79.0** (16 Apr 2026), see CODE_ANALYSIS §1. `package.json` → `repository: github.com/MaxZhadobin/TaoCoder`, keywords start with `cline`, all commands are `cline.*`, views `claude-dev.*`, Cline's tool enum (`ClineDefaultTool`) extended with `taocoder_*` tools, Cline endpoints and `.clineignore` still present. The site's own MCP-secrets post publishes paths `vendor/cline/src/...` [site]. Not Roo/Kilo.

**Modes [code].** Pipelines are hard-coded (`getStagePipeline`):

| Mode | Stages (code ids) |
|---|---|
| Architect | `architecture_discussion → architecture_doc_product_concept → _target_audience → _design_system → _architecture → _check_all → _roadmap → _decisions → _readme_ai` |
| Developer (default) | `clarification → data_collection → development → audit → report`, plus off-pipeline `rework` |
| Ops | `ops_diagnosis → ops_change → ops_validation → ops_escalation` |
| Debug | `debug_setup → debug_environment → debug_execution → debug_fix → debug_validation` |
| Free / Task | `execution` / `analysis` (Task may only write `./tasks/*.md`) |

Custom modes (TAO·MODES) are JSON on disk: `~/.taocoder/modes/` or `<repo>/.taocoder/modes/<id>/mode.json` + `stages/*.json` (prompt, allowed/forbidden tools, exit criteria, hooks). Mode Builder and the two Guide modes ship as such JSON modes in `resources/builtin-modes/` [code].

**Per-stage tool allowlist (Developer) [code]:**

| | clarification | data_collection | development | audit | rework | report |
|---|---|---|---|---|---|---|
| edit files | – | – | yes | – | yes | – |
| run commands | ask | ask | yes | ask | yes | – |
| change stage | yes | yes | yes | ask* | yes | ask* |
| `attempt_completion` | – | – | – | – | – | yes |

*(corrected)* "ask" = the stage's `requireConfirm` flag, which has no practical effect: it only forces a prompt when Cline's auto-approve is already off for that tool, and `taocoder_set_stage` never asks at all.

**Stage gate** (`taocoder_set_stage` handler) [code], in order: target is any stage in the pipeline (or rework), so stages can be skipped → `reason` + `evidence_refs` present; ids are validated only when given as an id object *(corrected)* → no exit criterion of the current stage is explicitly `false` (rework skips the review ones) → leaving audit/validation stages: every acceptance criterion has a non-pending verdict with comment; entering `report`: every AC = `pass` → custom modes only: `required_secrets`, `stage_exit` hooks (JEV, approval) → transition, `stage_history` append, **exit criteria of the target stage reset to false**, auto-plan items added.

Developer exit criteria [code]: clarification `has_task_spec, has_acceptance_criteria, constraints_defined, scope_confirmed, …`; development `implementation_done, tests_added, check_all_passed, code_modular, code_production_quality, no_hacks_or_workarounds, …`; audit `implementation_reviewed, tests_reviewed, docs_reviewed, integration_reviewed, security_reviewed, check_all_passed, …`.

**check_all.sh [code].** Nothing in the extension executes or parses `check_all.sh`. The stage prompt tells the model to run `bash check_all.sh` ("MUST be GREEN"); the model then sets `check_all_passed=true` via `taocoder_update_exit_criteria`. The "quality guard" is an instruction plus a self-reported flag. Logs conventionally go to `.taocoder/check_runs/` [site].

## 3. Memory: Task Context and the bounded prompt

**Storage [code].** `<repo>/.taocoder/tasks/<task_id>/task_context.json` (+ `task_context_meta.json`, `audit.jsonl` event log, `snapshots/<id>/`, `artifacts/diffs/`, `handoff_bundle.json`, `handoff_summary.md`). Fields: `task{spec, acceptance_criteria, constraints, implementation_plan ≤50}`, `stage`, `stage_history`, `exit_criteria`, `relevant_code[]` (path + line range + sha256 anchor; stale refs repaired by hash/fuzzy search), `notes[]` (tags hypothesis/decision/negative_knowledge/info), `changes[]` (diff refs), `execution_log`, `feedback`, `user_notes` (hidden from the agent), metrics, budgets.

**Prompt per request [code]** *(corrected)*. `[system, kernel, stored history ≤50k tokens, ephemeral tail]`. The kernel is one user message: header → chronological feed (newest first; outside the budget, never trimmed) → stage/spec/AC/constraints → system info → README_AI.md → last 5 done tasks → ALGORITHM ("Every response MUST be a tool call") → stage prompt → exit criteria → legend; 50k hot tokens (200k chars), last sections dropped first; snippets are the 25 *oldest* line refs × 150 lines; the kernel is cached between update-cycles. The plan and "KERNEL UPDATES" deltas go into the tail. The stored API history is cut to 20 messages after each update-cycle.

**Write paths into memory [code]:**
1. deliberate tool calls: `taocoder_update_task_spec`, `_add_relevant_code_ref`, `_add_note`, `_add_note_comment`, `_update_implementation_plan`, `_update_exit_criteria`, `_update_acceptance_criteria`, `_create_handoff`, `_self_delay`, `_jev_validate`, `_validate_mode`;
2. **update-cycle** *(corrected)*: every 5 new user-role API messages — each tool result counts, so ≈ every 5 tool calls (`taoCoderUpdateCycleBatchSize`) — or forced when kernel deltas exceed 10k tokens; it sees tool calls/results but not the model's reasoning; a separate LLM call ("You are a structured fact extractor… RAW_TAIL messages… are about to be PERMANENTLY DELETED") returns JSON (code refs, notes, plan statuses); a snapshot is taken first;
3. the owner, via the Task Context "Cockpit" panel (edit spec/plan/AC, notes, snapshot, rollback).

Metrics in `task_context.json` [code]: `api_call_count`, `total_cost`, `duration_ms`, `token_metrics{tokens_in, tokens_out, cache_writes, cache_reads}`, `tool_call_count`; breakdowns by **call type** `agent / handover / update_cycle / repair / crash_analyst`.

## 4. Triggers, autonomy, safety

- **Start**: chat (owner pastes roadmap phase "Выполняем Этап N"), **schedule** (`.taocoder/schedules.json`, runs only while VS Code is open; missed-run dialog run now/skip/reschedule), **handoff** (`taocoder_create_handoff` → new Developer task with `handoff_bundle.json`; knowledge migration is an LLM call), **self-delay** (same task id later). 10+ parallel tasks [site].
- **Autonomous runs** (scheduled/self-delay/inherited) *(corrected)*: the "AUTONOMOUS MODE… Do NOT ask the user" preamble exists but is never sent; autonomy comes from auto-answered follow-up questions, `auto_approve_tools`, and blocking of `rm`, `git checkout --` and non-safe commands unless auto-approve-all [code]. Cron runs in UTC.
- **Command safety** `classifyCommand` [code]: user blacklist → built-in blacklist (`rm`, `sudo`, `dd`, `mkfs`, `git reset --hard`, `git clean -f`, `curl|sh`, `iptables`, …) → user require_approval → user whitelist → built-in whitelist (ls/cat/grep, git status/diff/log, npm/pip/pytest, docker build/logs, …) → `unknown`. Dangerous/unknown/requires_approval prompt the owner — *(corrected)* except under auto-approve-all, where everything but `rm`/`git checkout --` runs unasked; the whitelist matches only the first command segment. Rules in `.taocoder/command_safety.json`.
- **JEV** [code]: external decision model (`typesafe/jev-1.13` via `api.typesafe.ai` or OpenRouter), **disabled by default**, threshold 0.7, 10 s timeout, fails open. Uses: `taocoder_jev_validate` tool; terminal guard for `unknown` commands (opt-in; *(corrected)* its verdict is computed but never changes the decision); `jev_validate` hooks in custom modes only. *(corrected)* The "Justification-Evidence-Verification" expansion does appear in the tool description and UI release notes.
- **Secrets** [code]: `{{SECRET:KEY}}` placeholders resolved right before `execute_command`; MCP/REST configs are auto-scrubbed into placeholders. Storage is `~/.cline/data/secrets.json` (plain JSON, mode 0600) after a migration from VS Code SecretStorage — contrary to the site's "SecretStorage / OS keychain" claim, but *(corrected)* inherited unchanged from upstream Cline ≥3.78.

## 5. The project lifecycle seen in the 24 documents

- Architect output = a fixed document set: PRODUCT_CONCEPT, TARGET_AUDIENCE, DESIGN_SYSTEM, ARCHITECTURE, CHECK_ALL (+ `check_all.sh`), ROADMAP, DECISIONS, README_AI. The TG/MAX/VK project's ADR-001 fixes "8 documents… README_AI.md last" [site]. Earlier projects (TAO·LLMHUB, June) use a looser set; Cayman ERP back-filled its architecture docs (dated 03.10.2026) [site/inf].
- README_AI comes in two flavours: a versioned "bible" (Milena, News, TG, VSL, Cortex) or an ever-growing status log appended by update cycles (CRM 2,312 lines, Cayman, LLMHUB) [site].
- Tasks per roadmap phase range ≈2 (Cortex) to ≈48 (News Analytics): fixes, rework, ops and doc updates are separate tasks [inf].
- Gates seen in projects' check_all: typecheck, lint, unit tests with coverage 80–90%, doc coverage 90–95%, integration, docker build, health checks; grep assertions that design tokens exist in code; auto-SKIP for missing modules [site].
- Deployment: `deploy_remote.sh` (commit → push → SSH) → `deploy.sh` (rebuild, migrations, checks) on a shared VPS behind a global nginx proxy with acme-companion [site].
