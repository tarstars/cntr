TAO·CODER Teardown

How the coding agent behind цнтр.рф/proof turns a product brief into code, and how its task logs become the numbers on that page. Rebuilt from 75 site pages, the 24 project documents embedded in /proof and the published VS Code extension (tao-coder 3.1.2), whose code was diffed against 12 releases of Cline to separate TAO's own 2.2 MB from the Cline 3.79 it was forked from.

One roadmap phase, start to finish

  1. A3A5

    The owner starts in Architect mode. The agent walks nine stages and writes one document per stage with the owner: product concept, audience, design system, architecture, the check_all.sh contract, the roadmap, decisions and finally README_AI.md, the “project bible” later tasks read. The model decides which documents a project needs and may jump between stages.

  2. A7C1

    The roadmap is cut into phases sized for one task. The owner selects a phase, adds it to the chat and writes «Выполняем Этап N». A Developer task starts with its own folder under .taocoder/tasks/. Tasks can also start from a cron schedule, a handoff from another mode, or a self-delay. A task in a custom mode first asks the vendor server for a launch from the owner's plan.

  3. C3

    Before every model call the extension rebuilds the request: Cline's system prompt; one kernel message rendered from task_context.json (a newest-first feed of code refs, notes and changes that is never trimmed, then spec, criteria, README_AI, the stage prompt and exit criteria); the stored history, which each update-cycle cuts back to 20 messages; and a fresh tail with the plan and whatever changed since the kernel was cached.

  4. D3

    The model must answer with exactly one tool call. Each call adds to the task's call counter, cost and duration. Duration is time spent inside model calls, so the 2,418 hours on /proof are about 48 seconds per call of model time, not working time.

  5. D7E5

    The stage's allowlist is applied twice: disallowed tools are removed from the tool list the model sees, and any that slip through are rejected with an error naming the stage that allows them. Clarification and data collection cannot edit files; only report can finish. The per-stage “needs confirmation” flags change nothing in practice.

  6. E5

    Shell commands are classified: blacklists, approval rules, then whitelists matched on the first segment only. Dangerous and unknown commands ask the owner unless auto-approve-all is on; then only rm and git checkout -- still ask. Secrets are written as {{SECRET:KEY}} and substituted only at execution time.

  7. D5C5

    Memory is written four ways: the agent's taocoder_* calls; an update-cycle every 5 tool results that extracts notes and code refs from recent tool traffic (it never sees the model's reasoning) and then truncates the stored history; a repair planner that rewrites an empty or broken plan or spec; and the owner's edits in the Cockpit panel.

  8. B7C7C8

    To change stage the agent calls taocoder_set_stage. The gate checks that no exit criterion of the stage is false and, around audit, that acceptance criteria have verdicts. The criteria are flags the agent sets itself or the owner ticks in the Cockpit. check_all_passed is one of them: nothing runs the script to confirm it. Failing audit sends the task to rework.

  9. B7A7A8

    The report stage ends the task. The owner goes back to the roadmap for the next phase; Ops mode deploys (deploy_remote.sh → deploy.sh → Docker) and Debug mode runs E2E tests against the running stack. On /proof that loop averages 2–48 tasks per roadmap phase, because fixes and rework are separate tasks.

  10. E3E4E6

    Outside the agent, a script in the site repo (scripts/generate-proof.ts with projects.json) rolls the task data of eight repos into the HTML block between PROOF_DATA markers and embeds 24 project documents. A handoff copies the parent task's cost into the child, so summed costs can count a chain twice.

  11. F3F4

    The same tool also writes the blog. Ten AI-industry reviews are signed «Статья написана ИИ инструментом TAO•MODES». Their Monday/Thursday cadence and the News Analytics project point to a scheduled custom mode, though no page says so outright.

Where the site and the code disagree

What the marketing pages and guide say, next to what version 3.1.2 of the extension actually does. None of these breaks the pipeline; they change how much you can trust the gate and the numbers.

Likely defects in v3.1.2

Found by reading the code against upstream Cline, not by running it, so treat each as probable rather than proven. Several of them change what the /proof numbers and the safety claims mean.

  • Replies over 5 minutes. each streamed chunk starts a 300 s timer that is never cleared and stops the stream; long replies end silently.
  • Slow approvals. a tool or approval pending for more than about 3 minutes throws “Tool execution timed out” and ends the turn loop.
  • Schedules. cron is evaluated in UTC whatever the timezone field says; dismissing the missed-run dialog does not stop the run; a self-delay resumes only if that chat is in the foreground.
  • Stage machine. the README_AI contract and the tool spec send the model to architecture_docs, which is not a pipeline stage; the acceptance-criteria tool always fails in Free mode.
  • Memory. the Cockpit's force-update button writes to the wrong file; change-visibility updates from the extractor are dropped; one kernel cache slot is shared by parallel tasks.
  • Command rules. an ungrouped regex makes git init and npm init “dangerous”.
  • Connections. MCP servers added through manage_connections are connected but not saved; a REST request with a missing key goes out with the literal {{SECRET:…}}.
  • Shipped leftovers. 11 debug beacons post tool names and file paths to 127.0.0.1:19345; a test script carries a hard-coded API key for a TaoBridge server; a PWA prototype and two 195 KB tailwind logs ship in the package.
